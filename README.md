# dsh-find-in-sessions

DeepSeek Harness 插件：`Ctrl+F` 呼出查找栏，按关键词检索**所有历史会话**的对话正文与工具输出，命中后打开那一段，用 F3 / ↑↓ 在命中之间前后跳。

## 为什么不用宿主自带的搜索

| 宿主自带 | 本插件 |
|---|---|
| 本机 profile 把 `session-query-sqlite` 配成 `openAt: never`，`/api/session/search` 一律返回 `SESSION_QUERY_SEARCH_DISABLED` | 自带索引，直接读会话日志，不依赖那个库 |
| `unicode61` tokenizer 把连续中文当一个 token，实测「插件」「本地搜索」命中数为 0 | 中文按 bigram 切词，两字词照常命中 |
| 每个会话只返回一条最佳片段，没有事件坐标，只能打开会话 | 返回每条命中的 `seq` + `turn`，跳到具体那一轮并高亮 |

## 架构：SQLite 索引

`lib/store.js` 用 Node 内置的 `node:sqlite` 建一个库，FTS5 索引 + 自建中文 bigram 分词。

**为什么自己做 bigram**：`unicode61` 把连续中文当一个 token；`trigram` 按 3 字符切，中文两字词凑不满窗口，索引用不上。入库前把中文切成两字窗口（「会话搜索」→ `会话 话搜 搜索`），查询侧同样切。两字查询正好是一个 token，三字以上是若干 token 的 AND。

**为什么不再常驻内存**：0.1 版把全部正文摊在进程里，落盘是 3.9 + 13.6 MB gzip，冷启动要解压 207 ms、解析 310 ms，工具那份解析后常驻内存远大于 53 MB JSON。索引化之后冷启动不开销、查询只读命中行、工具那份也不必整份进内存。

本机实测（2026-11-18，1150 个会话文件 / 双分区）：

| 项 | 实测 |
|---|---|
| 索引库 | **178 MB**（+ WAL 5 MB） |
| 规模 | 正文 12688 行 / 7.41 M 字符；工具 30223 行 / 43.06 M 字符 |
| 当前会话内检索 | 6–10 ms |
| 全局 2 字中文 | 12 ms |
| 全局单 ASCII 词 | 22 ms |
| 全局 4 字以上中文 | 3–7 ms |
| 全局单字中文 | **451–575 ms**（无 bigram 可用，退化成全表扫） |
| 冷启动 | 0（不再解压解析） |
| 工具分区首次构建 | 约两分钟（读完全部会话） |

两条硬性能约束写在 `search()` 的注释里：`exact` 命中时不把 text 拉回 JS；用 `MATERIALIZED` 保证 FTS 先跑（否则规划器会把 `instr` 排到前面，退化成 600 ms 的路径）。

**增量**：会话日志是 append-only 的，`list()` 的 `sizeBytes` 变了才进 `syncSession`，它按 `read(已读事件数)` 只读新增那段，并在库里记 `size` / `events` / `turn` 接续。

## 索引文件

```
~/.dsh/cache/dsh-find-in-sessions/index.db        # WAL 模式，可整套删掉重建
~/.dsh/cache/dsh-find-in-sessions/index.db-wal
~/.dsh/cache/dsh-find-in-sessions/index.db-shm
```

- 体积随语料线性增长，本机 1150 个会话对应 178 MB。删掉后下次启动自动重建（正文分钟级，工具要等第一次切到「工具」）。
- 同目录下的 `body.json.gz` / `tool.json.gz` 是 0.1 版的缓存，**0.2 起不再读取**，可以手工删除。
- 切词规则或表结构变化时 `INDEX_VERSION` 递增，旧库整份丢弃重建；单条会话读取失败只标记 `size=-1` 待重试，不会中断整份对齐。

## 用法

| 操作 | 键 |
|---|---|
| 打开查找栏 | `Ctrl+F`（当前会话）/ 双击 `Ctrl`（全部会话） |
| 关闭 | `Esc` |
| 在候选间移动 | `↑` `↓` / `F3` `Shift+F3` / `Shift+Enter`（上一处） |
| 打开选中的那一处 | `Enter`，或双击结果行（落点见下节） |
| 切换检索对象 | 点「正文 / 工具」按钮 |
| 切换时间窗口 | 点右侧下拉（1 天 / 3 天 / 7 天 / 30 天 / 全部，默认 7 天） |
| 切换角色 | 点「全部 / 我 / 助手」按钮（工具检索下无效，工具输出不区分角色） |

**检索范围没有按钮**，由快捷键决定：`Ctrl+F` 是「当前对话」，双击 `Ctrl` 是「全部会话」。输入框的 placeholder 会写明当前是哪一种。

面板宽度不够时，右侧那组控件会按断点分级让位（先隐藏角色与时间，再让位计数），保证输入框和命中导航始终可用。

上下键的行为分两种：

- **当前会话内**：边选边跳。命中就几处，跳转不换会话，翻起来连按即可。
- **全局检索**：`↑↓` 只移动选中，`Enter` 才跳过去——跨会话跳转会切走当前阅读位置、重建整屏，翻十条就是十次重建。这里与 IDE 的全局搜索一致。

`Ctrl+F` 原本是浏览器的页面内查找，本插件会拦掉它。

## 打开命中：四种落点

| 形态 | 落点 | 原因 |
|---|---|---|
| 当前会话 + 正文 + 消息数 ≤ 300 | 直接在对话里跳转并高亮 | 同一屏内挪动，比开个 tab 还快 |
| 当前会话 + 正文 + **消息数 > 300** | 右侧栏「命中预览」 | 宿主会话视图没有虚拟化，见下 |
| 全局检索 | 右侧栏「命中预览」 | 跨会话跳转会切走当前阅读位置、重建整屏 |
| 工具检索（任意范围） | 右侧栏「命中预览」 | 工具结果的 id 是 `callId`，会话视图里没有对应节点，跳过去必然落空 |

预览页给的是**命中的那一条 + 前后各一条**（到头或到尾就自然截断），关键词高亮，顶部的「会话定位」按钮固定在右上角、不随内容滚动，点击切到原会话并按 `messageId` 定位到那一处。

- **没装 `dsh-better-sidebar` 时**：全局检索退回跳转；工具检索没有可用的落点，会明说「工具命中需要在侧栏预览」，而不是做一次注定失败的跳转。
- 侧栏是可选增强，所以没有写进 `inject`——否则服务缺失会让整个插件不加载。
- **tab 只存坐标**（sessionId / seq / messageId / 关键词），正文按需再取。
- 同一条命中反复打开只聚焦同一个 tab；预览只从索引取正文，不读会话文件。

### 为什么超大会话不跳

宿主会话视图**没有虚拟化**：实测 `dsh-client-ui-conversation` 的 bundle 里 `Virtualizer` / `overscan` / `estimateSize` / `windowed` 全部零命中，`replaceWindow` / `prepend` / `hasMore` 只是**数据分页**——消息一旦加载就全量挂成 DOM。

本机最长的一个会话有 6773 条消息（33.4 MB 压缩 → 91.4 MB 解压 / 37324 个事件）。在这种容器上设一次 `scrollTop` 要把中间全部内容参与布局，浏览器直接卡死；把**官方的滚动条**拖到顶部同样卡——这两件事说明卡点在渲染，不在检索，也不在跳转代码。

所以阈值 300 条消息时就改走侧栏预览（纯文本，不碰会话渲染），并在状态栏说明原因。

### 不再有「退出回到原位」

「记 `scrollTop` 快照 → 退出时设回去」这一整套删掉了。它在无虚拟化容器上不成立：设一次要等全部布局算完，清高亮会改变内容高度触发重排、宿主的「跟随末尾」还会在下一帧再滚一次，于是只能靠 rAF + 120 ms 二次补设去抢，抢不抢得赢取决于宿主的渲染时序——那就是「设了又被覆盖」反复出现的来源。现在跳过去就停在那儿。

## 安装

```powershell
# 从 npm
dsh plugin --profile web add dsh-find-in-sessions

# 从本地源码（开发时）
dsh plugin --profile web add D:\DSH\创造模式\dsh-find-in-sessions
```

装完重启 `dsh web`。插件同时有宿主半和浏览器半，两半都在启动时加载。

- 只改 `lib/client.js`：刷新页面即可。
- 改 `lib/index.js` / `lib/store.js`：必须重启 `dsh web`。

## 行为边界

- **只读会话，只写自己的索引**：会话以 `read` 句柄打开，不改动会话文件；写入只有 `~/.dsh/cache/dsh-find-in-sessions/` 下的索引库。
- **两份索引，按 `kind` 分区**：正文与工具输出分开存、分开查。工具那份默认不建，第一次切到「工具」时才懒建（读全部会话，约两分钟），建好后常驻磁盘而不是常驻内存。
- **正文只索引看得见的正文**：`user/message`、`assistant/message` 里 `type: "text"` 的块；不索引 reasoning、工具调用参数、流式分片。`<system-reminder>` 注入块整块删除，运行时快照（`MNEMON RUNTIME MEMORY SNAPSHOT`、`[MNEMON]`、检查点正文等）按前缀整条丢弃。
- **长消息分块不截断**：正文单块 4000 字，一条超长消息占多行，结果行标「14k · 第 1/4 段」（0.1 版的正文 200k / 工具 20k 硬上限已取消）。
- **单次返回上限 200 条命中**；全局检索每个会话只采样最近 5 条、最多 60 个会话，卡片上的「显示全部 N 条」会按同一条件再取一次该会话的全量。
- **跳转靠宿主自己的加载器**：`ISession.loadThrough(seq)` 拉历史页，`data-chat-turn` 做锚点。目标轮次还没渲染时提示而不会乱跳。
- **非会话条目会被跳过**：`sessionPersistence.list()` 除了 `session-*` 还会列出 `mnemon-run-v1-*` 这类其他插件的运行记录，它们打不开，会被标记 `size=-1` 后跳过并记日志，不影响其余会话。
- **增量的边界**：会话级按 `sizeBytes` 判断变没变；`list()` 有 5 秒 TTL，所以正在写的会话要靠请求里带的 `sessionId` 额外 `stat` 一次才能立刻看到变化。
- **索引不会自己过期**：会话变了会在下次检索时增量对齐；会话文件消失会在下次整体对齐时从库里清掉。

## 已知限制

- 召回是**字面子串**，不是分词或语义：搜「本地搜索」不会命中「本地全文搜索」。
- 大小写不敏感（对含字母的关键词，由 FTS 的 `unicode61` 折叠），但不做全半角、简繁、拼音归一化。
- **单字中文很慢**（451–575 ms）：一个汉字凑不出 bigram，FTS 用不上，只能全表 `instr`。三字以上中文会切出多个 bigram，需要回原文复验，比两字慢但仍是毫秒级。面板会给出提示。
- 工具输出默认**不进索引**——它单独一份，要手动切到「工具」才会建立。
- 当前正在写的会话，最新几条可能还没落盘；再搜一次即可。
- **与宿主内部实现耦合较深**：依赖 `[data-conversation-session]`、`[data-conversation-scroll]`、`[data-chat-turn]`、`[data-chat-node-key]`、`[data-chat-call-id]`、`data-row-key="session:…"`、`[data-disclosure-row][aria-expanded]` 等属性，以及 `ISession.loadThrough`。宿主改动这些没有稳定性契约，坏了的表现是静默退化（跳不过去 / 位置不对），不报错。

## 开发

```powershell
node --check lib/index.js
node --check lib/client.js
node --check lib/store.js
```

无构建步骤、无第三方运行时依赖：`lib/*.js` 就是分发产物。`lib/store.js` 依赖 Node 内置的 `node:sqlite`（Node 22.5+ 提供，本机 v24 已稳定）。

`lib/client.js` 的 `Ctrl+F` 监听挂在 `window` 的 capture 阶段并 `preventDefault`，这是刻意的取舍，改动前先确认是否还要抢浏览器原生查找。
